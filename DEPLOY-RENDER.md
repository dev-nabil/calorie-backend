# Deploy the backend on Render (free)

The API runs on Render as a plain Node service: no Docker. `render.yaml` in this folder describes it
(a Render "Blueprint"), so most of the setup is filled in for you.

This gives you a **test server** for the app team: real database, real Gemini, Google sign-in. It is not
a production setup. See [Going to production](#going-to-production) for what changes.

## What the free plan gives you

| | Free web service |
|---|---|
| Memory | 512 MB (the API used about 310 MB in a local test with the same settings) |
| Sleep | Stops after 15 minutes with no requests. The next request wakes it in about 1 minute |
| Hours | 750 a month per Render workspace, shared by all free services in it. One service running all month fits |
| Disk | Wiped on every deploy and every wake-up |
| Background workers | Not on free. The API runs its queue work in the same process (`ROLE=all`) |

What the sleep means for the app:

- The first call after a quiet period takes about a minute. The app may show a timeout once; try again.
- Reminders still ring: the phone schedules them itself.
- Rate limits and queued jobs live in memory, so they reset when the service sleeps.
- Photos saved with `STORAGE_DRIVER=local` disappear when the service sleeps or redeploys. Use R2 if
  photos must last (see [Optional upgrades](#optional-upgrades)).

## Before you start

You need:

1. A [Render](https://render.com) account, signed in with GitHub, with access to the
   `dev-nabil/calorie-backend` repository (the backend-only copy of `nouri-backend/`).
2. A MongoDB Atlas cluster (the free M0 is enough) and its connection string.
3. A Gemini API key (the same one as in your local `nouri-backend/.env`).

## Step 1: let Render reach MongoDB Atlas

Render's free plan has no fixed outgoing IP address, so Atlas must accept connections from anywhere.

1. Atlas → **Network Access** → **Add IP Address** → **Allow access from anywhere** (`0.0.0.0/0`) → Confirm.
2. Atlas → **Database** → **Connect** → **Drivers**. Copy the connection string.
3. Put your database user and password in it, and make sure the database name `/nouri` is in it:

   ```
   mongodb+srv://USER:PASSWORD@CLUSTER.mongodb.net/nouri?retryWrites=true&w=majority
   ```

   Without `/nouri` the data lands in a database called `test`.

The database user's password is the only thing protecting the data now, so use a long random one.

## Step 2: create the service from the Blueprint

1. Render dashboard → **New** → **Blueprint**.
2. Pick the repository **`dev-nabil/calorie-backend`**, branch `main`. Render finds `render.yaml`.
3. Render shows the service `nouri-api` and asks for the values marked "sync: false":

   | Key | What to enter |
   |---|---|
   | `MONGODB_URI` | the connection string from step 1 |
   | `GEMINI_API_KEY` | your Gemini key |
   | `REDIS_URL` | leave empty |
   | `EMAIL_API_KEY`, `EMAIL_FROM` | leave empty (sign-in codes go to the Render log, see step 4) |

4. Click **Apply**. The first build takes a few minutes. The 4 secrets (`JWT_*`, `OTP_PEPPER`,
   `LEDGER_PEPPER`) are generated by Render; never change `LEDGER_PEPPER` later.

**Using the main repo instead** (`dev-nabil/calorie-scanner`, where the backend is the `nouri-backend`
folder): choose **New** → **Web Service** instead of Blueprint, set **Root Directory** to `nouri-backend`,
**Runtime** Node, **Instance type** Free, copy the **Build Command**, **Start Command** and
**Health Check Path** from `render.yaml`, and add every environment variable from `render.yaml` by hand
(for the 4 secrets, run `openssl rand -base64 32` once for each).

> **Do not skip `DEV_ROUTES=false`.** Without it the test server is in development mode with the
> `/v1/dev/*` helpers open to anyone: they read the last sign-in code sent to any email and move the
> server clock. Check after deploying: `https://<your-url>/v1/dev/last-otp?email=x@y.z` must answer 404.

## Step 3: check that it runs

Open `https://nouri-api.onrender.com/v1/health` (Render shows the real address at the top of the
service page; it has a suffix if the name was taken). You should see:

```json
{"status":"ok","role":"api", ... ,"checks":{"mongo":"up","redis":"memory"}}
```

`"mongo":"up"` means the database connection works. `"redis":"memory"` is expected without `REDIS_URL`.

If the deploy fails, open **Logs**: a missing or wrong environment variable is named there.

## Step 4: point the app at it

In `nouri-mobile/lib/app/env.dart`, set both addresses to your Render URL plus `/v1`:

```dart
static const _debugApi = 'https://nouri-api.onrender.com/v1';
static const _releaseApi = 'https://nouri-api.onrender.com/v1';
```

Then rebuild the app.

Signing in on the test server:

- **Google** works as it does locally (`GOOGLE_CLIENT_IDS` is already in `render.yaml`).
- **Email codes** are not mailed. Render → `nouri-api` → **Logs**, search for `SIGN-IN CODE`. Fine for a
  few testers; for real mail set up Resend (below).

## Updating

Every push to `main` of `dev-nabil/calorie-backend` deploys again by itself (`autoDeploy: true`).
Changes made in the main repo reach Render once they are copied to the backend repo.

## Optional upgrades

All of these have free tiers.

- **Email that really arrives:** create a [Resend](https://resend.com) account, verify a domain, then in
  Render → Environment set `EMAIL_DRIVER=resend`, `EMAIL_API_KEY=<key>` and
  `EMAIL_FROM="Nouri <hello@your-domain>"`.
- **Photos that last:** create a Cloudflare R2 bucket and an API token with read and write access to
  it, then set `STORAGE_DRIVER=s3`, `S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com`,
  `S3_REGION=auto`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`.
- **Redis (queues off the request path):** Render **New** → **Key Value**, Free, same region, maxmemory
  policy `noeviction`. Copy its **Internal Key Value URL** into `REDIS_URL`. The free instance keeps
  nothing across restarts, which is fine for a test server.
- **Testers share one IP in the rate limits:** behind Render's proxy every request can look like it comes
  from the same address. If testers get "too many requests", set `TRUST_PROXY=3` (the hop count Render
  users report) and check that limits still apply per person.

## Going to production

The free plan is not suitable for real users: it sleeps, and its disk and memory reset. For a launch:

1. Use a paid instance (Starter or larger) so it never sleeps, and a paid Key Value with persistence.
2. Set `NODE_ENV=production`. The API then refuses to start until all of these are set:
   `REDIS_URL`, `STORAGE_DRIVER=s3` (R2), `EMAIL_DRIVER=resend`, `TURNSTILE_SECRET`,
   `INTEGRITY_DRIVER=device` (with the Play Integrity and App Attest settings from `.env.example`),
   `AI_PROVIDER=gemini` and the 4 secrets. Remove `DEV_ROUTES` and `SWAGGER_ENABLED`; production turns
   both off by itself.
3. Set `REVENUECAT_API_KEY` and `REVENUECAT_WEBHOOK_SECRET`. Without them purchases are not checked, which
   is acceptable only on a test server.
4. Set `TRUST_PROXY` to the checked hop count, and `CORS_ORIGINS` to the web and admin addresses.

`pnpm env:doctor` (run locally with the same values in `.env`) lists what is real and what is still fake.

## Troubleshooting

| Problem | Fix |
|---|---|
| Build fails at `npm install -g pnpm` | Change the Build Command to `corepack enable && pnpm install --no-frozen-lockfile --prod=false && pnpm build` |
| Build fails at `tsc` / `nest` not found | Keep `--prod=false` in the Build Command: the compiler is a dev dependency |
| Logs say `Invalid environment` | The message names the variable. Fix it under Environment and redeploy |
| Health shows `"mongo":"down"` or the deploy times out | Atlas Network Access (step 1), or the password in `MONGODB_URI` has a special character that needs URL-encoding |
| App says it cannot reach the server | The service was asleep: wait a minute and retry. Check the URL in `env.dart` ends with `/v1` |
| Food scan fails, everything else works | Fixed on 8 Nov 2026 (redeploy the latest `main`): upload URLs were `http://` behind Render's proxy and the photo upload got a 307 redirect. With local storage the upload endpoint now also works with `DEV_ROUTES=false` |
